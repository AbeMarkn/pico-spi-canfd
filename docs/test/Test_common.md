# テスト共通方針・手順

文書版: `0.1.0`。関連: DESN-SW-014。本書は全体の試験計画。実施済みの部分と未達・未実施は[結果書](results/TEST-SPEC-DESN_result_001.md)を正本とする。

## 1. 実施段階とID

1. 実機なし自動: 各系列の001〜099。ホストアプリ、機器APIの代替、仮想単調時計、仮想シリアル、仮想ファイル異常等を用いる。内部関数を直接調べるのは設計テストに限定する。
2. 実機あり自動: 101〜199。配線と測定器を準備した後、操作・刺激・判定・証跡取得は自動化する。
3. 実機あり手動: 201〜299。目視、配線照合、実キーボード、手動電源操作など、自動化しづらい項目。

OPEN-005はユーザー指定で保留中。実装開始と接続済みPico／N947での実通信試験を明示指示されたためE0とE1の通信試験を実施した。E2の電気測定は保留を維持する。PicoはOS／RTOSなしのMicroPython安定版RPI_PICO UF2（今回確認1.29.0）を対象とし、環境構築時の実際の採用版とUF2のハッシュを記録する。E3はPWM統合時の別段階とする。

正常系は`Test_for_Specification.md`と`Test_for_Design.md`、それ以外は各`_non_normal.md`に分離する。番号の若い実機あり自動試験を先に実施する。今回の実通信はユーザーが接続・稼働済みの評価機を使用し、電気測定を実施した記録にはしない。

## 2. 仕様テストと設計テストの区別

仕様テストは利用者の入力、GUI、公開USB境界、ホストログ、バス上のフレームで評価する。実機なしでもGUIイベントや代替機器の外部境界を使い、私有関数・内部FIFOの状態を合否条件にしない。

設計テストはレジスタ、SPI、API、状態機械、Queue、IRQ、メモリ、要求番号・世代、エラー処理を直接観測してよい。実機なし自動試験はpytestで自動化し、人の確認を途中に挟まない。

## 3. 共通環境と試験データ

- E0: 実機なし環境。指定のmacOS Tahoe 26.6.2／Windows 11と、環境構築時の最新安定版CPython（今回確認3.14.7）、GUI自動操作環境、仮想USB機器、仮想時計、隔離したログ保存先。実際のOSビルド・CPU・Python・Tcl/Tk・依存版を記録する。別OSで行う補助確認を指定OSの検証完了に代用しない。
- E1: 通常構成はPicoと対象モジュール、N947ネットワークの相手2台の計3台、CAN配線長30 cm以内、二端終端、USBホスト。PicoのP3開放・120 Ω非実装を記録する。CAN FDアナライザは受動・追加終端なしで波形を観測し、相手アプリの受信証拠とは分ける。自動対向機を使う場合は相手一台を置換して3ノードを維持するか、追加する別構成を明記する。旧0x100試験は既存の同ID送信を停止し、受信フィルタ適合を確認する（OPEN-018）。
- E2: E1にロジックアナライザ／オシロスコープ、自動電源スイッチ、必要なバス障害発生器を追加。自動化できない測定は手動系列で行う。
- E3: 将来のPWM同居版。CAN単独版があるだけでは実施可能としない。統合時の具体的な起動・例外条件の記録（OPEN-012）が前提。

回帰確認用の設定Aは標準0x100、データ11〜18（HEX、8バイト）、500 ms。回帰確認用の設定Bは拡張0x18FF0101、データ21〜2C（HEX、12バイト）、500 ms。A・BはFD、調停500 kbit/s・データ2 Mbit/s・BRS=1を使用する。Classical用の条件A-CはAのfdf=false・brs=falseとし、8バイトのまま全区間500 kbit/sで送る。いずれも設定確定後にセッションを開始する。

通常運用の設定T1〜T4は[DESN-SW-002](../Design.md)を正本とする。T1は10 ms・Classical8バイト、T2は100 ms・Classical8バイト、T3は1000 ms・拡張FD64バイト、T4は10000 ms・拡張FD64バイトで同時稼働させる。ClassicalはBRS=false、FDはBRS=true。標準／拡張の具体ID・データ例は暫定で、実バスの割当確認後に固定する。A・B・A-Cは一般機能と500 msの既存評価目標用に残し、通常設定を置き換える試験入力として使う。

T1〜T4の実機評価はセッション時間を120秒に設定する。キー受付時刻は各IDで異なるため、実測の予定数は各開始時刻とセッション期限の半開区間から求める。全IDが同じ時刻0で始まる実機なしの60秒基準なら、予定投入数は6000／600／60／6件、合計6666件。期限と同値の投入を数えない。相手がN947の参照2チャネルなら定常RX12件/秒を基準候補とし、実際の相手送信時刻・フレームを証拠として用いる。

送信データの受信検証は既知の連番入り刺激を用い、生成数・バス観測数・Picoからの送出数・ログ数・GUI累積数を別に記録する。平均値だけで欠落や重複を見逃さない。TX成功は対向機／アナライザとTEF由来ログの両面で評価する。

## 4. 共通実施手順

1. 対象Test IDのSPEC／DESN／OPENを読み、期待値と採用設定を固定する。
2. 機器版、FW版、ホスト版、MicroPython版、commit、OS、配線、電源、P3、相手設定を記録する。
3. 前のセッションとログを分離し、指定初期状態にする。
4. 各テストの刺激を与え、外部出力または設計観測点の証跡を取得する。
5. 期待結果と照合し、新規の結果ファイルへ実際の結果を記録する。
6. 失敗時は原因仮説、再現条件、影響する仕様／設計を記録し、修正後も過去結果を上書きせず次の連番を使う。

OPEN-006の容量・評価目標とOPEN-009の停止待ち上限は採用済み。通常の送信負荷はT1〜T4、構成は3台・30 cm以内に具体化した。新たな10／1000／10000 msのジッタ閾値、実際のOSビルド・CPU・依存版・測定器と受信負荷上限はOPEN-015に残す。最大無欠落レートは特性評価で求め、条件がないまま無欠落合格としない。文書の数値を実測値へコピーしない。

採用目標の観測点は、起動＝接続照合開始から送受信準備完了、初回投入＝ホストキー受付からPicoのTXREQ反映、周期ジッタ＝Pico予定期限からTXREQ反映、GUI遅延＝ホスト受信から表示反映とする。バス上の実送信時刻は調停遅延を含む別値として記録する。両形式の短いフレームとFD64バイト、単独送受信と混在負荷を別々に評価する。

## 5. カバレッジ・評価観点

実機なし設計テストでC0（文・ステートメント）とC1（分岐）を測る。重点は設定境界、状態遷移、停止優先、重複要求、時刻周回、Queue満杯、例外、CRC・ECC、部分I/O。C0／C1の数値目標は実装構成決定後に定め、未到達やハード固有で測れない分岐の理由を残す。網羅率だけを正しさの証明にしない。

正常、境界、異常、操作ミス、起動直後、長時間、同時入力、高速入力、USB断、メモリ不足、ストレージ異常、電源投入／切断を対象とする。センサー異常、電池劣化、音声・画像変換はその機能がないため対象外。ネットワークOSのMutex／Semaphore等を使わないPico側で、項目充足のためだけに機能を追加しない。

## 6. 結果と証跡

`results/TEST-SPEC-xxx_result_001.md`または`results/TEST-DESN-xxx_result_001.md`から実施回ごとに増分する。未実施用テンプレートは空欄を維持し、実施結果は別ファイルに記録する。証跡はログ、通信トレース、CANキャプチャ、波形、GUI画像等の実際のファイルを参照する。今回の集約結果はTEST-SPEC-DESN_result_001.md。生ログはevidence-001.zip、集計はanalysis-120s-001.json。計画73件とpytestのケース数を同一視しない。

電源断・接続断・ストレージ不能で証跡が保存できなかった場合も、その限界と別観測点の記録を残す。欠落数不明を0件にしない。

## 2026-09-14 受入条件追補

ユーザーの明示指示により、SPEC-NF-002の周期精度については現状実測性能をREADMEに記載する条件で許容する。元の評価目標・実測Failは履歴として維持し、目標達成とは扱わない。優先順位をGUI実操作、再接続・通信断・ログ保存へ変更する。GUIの自動ロジック試験と実操作確認は区別する。早期時間満了、誤送信、停止不良、データ不一致などの機能不具合は、この性能許容に含めない。追加評価はTEST-SPEC-DESN_result_002.mdを参照する。
