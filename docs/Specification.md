# 仕様書

文書版: `0.1.0`。出典は添付要求プロンプトと画像。開発版の実装・試験結果は[結果書](test/results/TEST-SPEC-DESN_result_001.md)へ分離しています。仕様の目標を実測達成値へ読み替えません。

## 1. 入力の整理

**確定事項**: USB接続のホストからCAN FD送受信を操作する。受信のID別HEX表示、送受信テキストログ、エラーの別ログ、キーによる即時・周期送信、標準／拡張ID、可変データ長、重複入力抑制、指定IDの停止、設定検証、有限の最大送受信時間を扱う。

**制約事項**: 初代Picoと添付モジュールを使用し、SPI0と指定配線を基本とする。機器側はOS／RTOSなし、ホストOSはmacOS Tahoe 26.6.2とWindows 11。Python／MicroPythonは環境構築時の最新安定版を選ぶ。制御用Python・制御設定は機器側、送受信データ・ログはホスト側に保存する。日本語文書・コメント、少数ファイル、SemVerを用いる。実装開始・実機試験の指示を受領済み。具体的なデバイスと配線は設計書に集約する。

**今回の回答による確定事項**: N947ネットワークへ接続し、調停500 kbit/s／FDデータ2 Mbit/sに合わせる。同一IDは置換。設定・ログ準備後の受信有効化から有限時間を計測する。Classical CANとCAN FDの両形式を送受信する。推奨された容量・性能目標・停止・ログ方針を採用する。4 IDを同時に周期送信し、50／500 msはClassical・8バイト、1000／10000 msは拡張IDのCAN FD・64バイトとする。

**確認待ち**: 現物の電気条件はユーザー指定で後日の測定まで保留。水晶20 MHzの仮定、基板電気条件、2 Mbit/s用ビットタイミング・TDCの実測、WindowsとGUIの操作適合、高負荷での実効受信レート、ログ末尾の停電耐性は未確認。採用した目標と達成済みの性能を区別する。

終端は端点の終端担当時だけ有効にする。実環境は相手2台と自分の計3台、CAN配線長30 cm以内。自ノードの終端ジャンパは開放、120 Ω抵抗は非実装と回答された。

## 2. 機能仕様

| 仕様ID | 利用者から見た要求 |
| :--- | :--- |
| SPEC-F-001 | macOS Tahoe 26.6.2またはWindows 11のPCから、USB接続した装置のCAN送受信を操作できる。指定環境での動作は実装後に検証する。 |
| SPEC-F-002 | 設定・ログ準備後の受信有効化から期限または停止まで、送信キー操作の有無によらずCANを継続受信してホストへ送る。Classical CANとCAN FDを同じセッションで受信できる。 |
| SPEC-F-003 | 受信データをGUIへHEX表示し、CAN IDごとに振り分ける。標準IDと拡張ID、およびClassical／FDの形式を区別できる。 |
| SPEC-F-004 | 送信データと受信データをホスト上のテキストログに保存する。 |
| SPEC-F-005 | 指定キーで登録データの周期送信を開始する。初回は一周期待たずに送信を要求し、その後は指定周期で繰り返す。通常運用は4 ID同時送信で、50／500 msはClassical・8バイト、1000／10000 msは拡張IDのCAN FD・64バイト。 |
| SPEC-F-006 | 標準11ビットIDと拡張29ビットIDに対応し、Classical CANデータフレームとCAN FDフレームを送受信できる。同じID種別・IDの送信データ／形式を変えると、既存の周期送信を置換する。 |
| SPEC-F-007 | データ長を可変にできる。ホスト起動時に全送信設定を検証し、不正なID、データ長、データ値等を指摘して修正を求める。曖昧な値で送信しない。Classicalのデータ長は0〜8バイト、FDは0〜8／12／16／20／24／32／48／64バイトとする。Classicalの9バイト以上、FDで表現できない9バイト、30ビットIDを受理しない。 |
| SPEC-F-008 | 受け付けたキー、CAN ID、データ、周期、開始／停止内容をホストへ表示する。同一キー・同一データの重複開始入力を受け付けない。 |
| SPEC-F-009 | キー操作で特定CAN IDの周期送信を停止できる。停止後は対応する開始キーを再び受け付ける。 |
| SPEC-F-010 | 標準ID用と拡張ID用の送信サンプル設定をそれぞれ一つ以上用意する。今回の通常運用例は指定周期の4 IDとする。 |
| SPEC-F-011 | ホストで最大送受信時間を定義でき、その時間に達すると送受信を停止する。無限のデータロギングを防ぐ。計測起点は設定・ログ準備後の受信有効化。初期値60秒、設定範囲1〜86400秒で、キー操作によって期限を延長しない。 |
| SPEC-F-012 | バスオフ等のエラー発生時には最新エラーをGUIへ簡潔に表示し、送受信ログと分けたエラーテキストログをホストへ保存する。 |
| SPEC-F-013 | 装置の制御ソフト・制御設定を装置内に保存し、ホストを交換してもCAN制御環境を引き継げる。送受信データとログはホストに保存する。 |

| SPEC-NF-006 | 将来、既存50 Hz PWM機能と一台の装置に同居できることを念頭に設計する。今回の設計段階で既存PWMソフトを改変・統合する要求ではない。 |

## 4. 採用済み方針と残る確認条件

- 起動・応答・周期の評価目標と容量制約はSPEC-NF-002のとおり採用。最大無欠落レート、負荷条件、保存可能容量、実電源電流はOPEN-005・OPEN-015で確認する。
- バスオフ停止・明示再開、有限の停止待ち・ログ排出を採用。Watchdogと接続監視の具体方式は設計書に記す。電源断の末尾ログ損失と外付けCANの強制停止限界はOPEN-010・011に残す。
- 初期評価は管理された机上環境とする。部品単体定格を装置全体の温湿度・サージ・絶縁保証に転用しない。寸法・重量・費用の追加数値要求は設けない。
- 電池、充電、電池保護、音声・画像変換、センサーの測定機能: 対象外。要求に含まれないため追加しない。

Classicalのリモートフレームは受信時に区別して記録する。リモート要求の送信・自動応答は今回のデータ送受信機能に追加しない。

仕様から設計・テスト、および逆方向の対応は[トレーサビリティ](test/Traceability_Matrix.md)を正本とする。

## 2026-09-14 受入条件追補

ユーザーの明示指示により、SPEC-NF-002の周期精度については現状実測性能をREADMEに記載する条件で許容する。元の評価目標・実測Failは履歴として維持し、目標達成とは扱わない。優先順位をGUI実操作、再接続・通信断・ログ保存へ変更する。GUIの自動ロジック試験と実操作確認は区別する。早期時間満了、誤送信、停止不良、データ不一致などの機能不具合は、この性能許容に含めない。追加評価はTEST-SPEC-DESN_result_002.mdを参照する。
